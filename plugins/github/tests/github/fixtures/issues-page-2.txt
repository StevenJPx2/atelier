No I/O and no dependencies; the traits below are how it reaches the world.\n\n### The pipeline\n\nEach issue atelier takes moves through one state machine. Its phase is kept in `state.json`; every poll turns what the plugins see into events, and one pure function moves the phase and names the actions:\n\n```rust\nlet pipeline = Pipeline::new(5, [(\"critic\", 2)]);\n\nlet open = Phase::Open { rounds: 4 };\n\nlet (next, actions) = step(open, Event::RoundFailed, &pipeline);\n// → (Blocked(RedRounds), [Interrupt, Unmark(Working), Mark(Blocked), Comment(..)])\n```\n\n`Pipeline` comes from the project's config: `red_rounds`, and the project's [stages](#adding-a-step) in order, each with its `<stage>_rounds` limit. Core knows how many stages there are and their limits, never what they are.\n\nGetting started is three phases, each one action that atelier takes and confirms:\n\n```mermaid\nstateDiagram-v2\n    direction LR\n    [*] --> Claiming: Requested\n    Claiming --> Preparing: Claimed\n    Preparing --> Starting: WorktreeReady\n    Starting --> Building: AgentStarted\n    Claiming --> Blocked: StartFailed\n    Preparing --> Blocked: StartFailed\n    Starting --> Blocked: StartFailed\n```\n\nThen the builder works, and atelier follows its pull request through the forge and the project's stages:\n\n```mermaid\nstateDiagram-v2\n    direction LR\n    Building --> Open: PullRequestOpened\n    Open --> Open: RoundFailed, under red_rounds\n    Open --> Stage: AllPassed\n    Stage --> Stage: StagePassed, more stages\n    Stage --> Green: StagePassed, the last\n    Stage --> Open: Pushed\n    Green --> Ready: MarkedReady\n    Ready --> Done: Merged\n```\n\nThe whole machine is one `match`:\n\n```rust\npub fn step(\n    phase: Phase,\n    event: Event,\n    pipeline: &Pipeline,\n) -> (Phase, Vec<Action>) {\n    use {Action::*, Event::*, Phase::*};\n\n    match (phase, event) {\n        (Untracked | Stopped, Requested) => {\n            (Claiming, vec![Mark(Working), Unmark(Build)])\n        }\n        (Blocked(_), Requested) => {\n            (Claiming, vec![Mark(Working), Unmark(Build), Unmark(Blocked)])\n        }\n        (Claiming, Claimed) => (Preparing, vec![CreateWorktree]),\n        (Preparing, WorktreeReady) => (Starting, vec![StartBuilder]),\n        (Starting, AgentStarted) => (Building, vec![CommentSession]),\n        (Claiming | Preparing | Starting, StartFailed) => {\n            block(Reason::Start, vec![])\n        }\n\n        (Building, PullRequestOpened) => (Open { rounds: 0 }, vec![]),\n        (p, Pushed) if p.has_pull_request() => (Open { rounds: p.rounds() }, vec![]),\n        (Open { rounds }, RoundFailed) => {\n            let rounds = rounds.saturating_add(1);\n\n            if rounds >= pipeline.red_rounds {\n                block(Reason::RedRounds, vec![Interrupt])\n            } else {\n                (Open { rounds }, vec![])\n            }\n        }\n        (Open { rounds }, AllPassed) => pipeline.stage(0, rounds),\n        (Stage { index, rounds }, StagePassed) => {\n            pipeline.stage(index.saturating_add(1), rounds)\n        }\n        (Stage { index, .. }, StageFailed { rounds })\n            if rounds >= pipeline.limit(index) =>\n        {\n            block(Reason::Stage(index), vec![Interrupt])\n        }\n        (Green { rounds }, MarkedReady) => (Ready { rounds }, vec![]),\n        (p, Merged) if p.has_pull_request() => {\n            (Done, vec![CloseIssue, Unmark(Working), RemoveWorktree])\n        }\n        (p, ClosedUnmerged) if p.has_builder() => {\n            block(Reason::Closed, vec![Interrupt])\n        }\n\n        (p, Unmarked | IssueClosed) if p.has_builder() => {\n            (Stopped, vec![Interrupt, Unmark(Working)])\n        }\n        (p, Unmarked | IssueClosed) if p.is_working() => (Stopped, vec![Unmark(Working)]),\n        (Untracked, LostTrack) => block(Reason::LostTrack, vec![]),\n\n        (p, _) => (p, vec![]),\n    }\n}\n```\n\n- `pipeline.stage(i, rounds)` is `Stage { index: i, rounds }` with the action `StartStage(i)` when the project has an `i`th stage, and `Green` when it has no more. With no stages, every check passing goes straight to Green.\n- `block` moves to Blocked and adds three actions to those it is given: unmark working, mark blocked, and a comment saying why.\n- `has_builder` is true from Building to Ready, `has_pull_request` from Open to Ready, and `is_working` from Claiming to Ready.\n\nThe events, and where each comes from:\n\n| Event | From |\n| --- | --- |\n| `Requested` | A tracker: the build mark on an issue its filter matches |\n| `Claimed`, `WorktreeReady`, `AgentStarted`, `StartFailed` | atelier's own actions, confirming or failing |\n| `PullRequestOpened`, `Pushed`, `RoundFailed`, `AllPassed`, `MarkedReady`, `Merged`, `ClosedUnmerged` | The forge, on the issue's branch |\n| `StagePassed`, `StageFailed` | The plugin of the current stage, with how many rounds it has failed |\n| `Unmarked`, `IssueClosed`, `LostTrack` | A tracker: a person removed the working mark, closed the issue, or marked one atelier never claimed |\n\n- **The working phases** are Claiming to Ready. Every way out of them removes the working mark, and every way out after Starting interrupts the builder.\n- **An event that does not apply** to a phase changes nothing and names no action, so `step` is total and a repeated event is harmless. A stage that fails under its limit changes nothing: the builder hears its findings, fixes them and pushes, and the checks and stages run again from the start.\n- **Each action confirms itself.** atelier carries out an action, then feeds its result back as the next event (`Claimed`, `WorktreeReady`, `AgentStarted`, or `StartFailed`). The phase is saved before each action, so after a crash the next poll finds the issue in Claiming, say, and repeats the claim, which is idempotent.\n- **The builder moves the later phases**, by pushing, opening the pull request and marking it ready; atelier only observes those through the forge, and steps in at the limits.\n\n### Events from a poll\n\nA poll compares what the plugins see with each issue's phase and names the events, also in pure code:\n\n```rust\nlet seen = Seen {\n    open: true,\n    marks: Marks::default().with(Mark::Working),\n    pull_request: Some(PullRequest::Open { number: 31, draft: true, failed_rounds: 2, checks: Checks::Failed }),\n    stage: None,\n};\n\nlet events = events(Phase::Open { rounds: 1 }, &seen);\n// → [RoundFailed]\n```\n\nA poll gathers what the plugins see on the project's thread; the worker turns it into events, steps each issue, and carries out the actions through the plugins:\n\n```rust\nlet plugins = Plugins {\n    trackers: vec![Source { name: \"github\", tracker: &github, filter }],\n    forge: &github,\n    agent: &opencode,\n    worktrees: &git,\n};\n\nlet seen = observe(&project, &plugins, &state)?;\n\nlet report = act(&seen, &mut state, &project, &plugins, &mut save)?;\n// report.steps → [(github#12, Claiming → Preparing), …]\n```\n\nEach poll lists each tracker's issues marked build, with the filter, and marked working, so an issue atelier never took is found. Core sees marks (`Build`, `Working`, `Blocked`), not label names; each issue's own tracker maps them, on GitHub to `atelier:build`, `atelier:working` and `atelier:blocked`. The marks show the phase to a person: build before Claiming, working through the working phases, blocked in Blocked. Core finds an issue's pull request through the forge, by the issue's branch, so the issue and the code can live in different places. A failed round is a head commit of the pull request with a failed check. GitHub closes issues by itself only on merges into the default branch, so atelier closes them, through the tracker, on merge into any base.\n\nCore also holds the builder's contract, `prompts/builder.md`, built in and naming no tracker, forge, agent or language:\n\n- Read the issue with its comments, and the project's `AGENTS.md`. Build what the issue asks, nothing more.\n- Commit in Conventional Commits, push to its branch, open a draft pull request into the base that names the issue as the tracker writes it (`Part of #12`, `Part of CHF-12`).\n- Build, commit, push. CI runs the checks and the project's stages follow; end the turn between events, since failed checks, findings and reviews arrive as messages.\n- On a failed check or a finding: read it, fix the cause, push. Never push again only to retry.\n- After `red_rounds` failed rounds, or when only a person can unblock it: comment on the pull request with what blocks it, mark the issue blocked, stop.\n- When every check passes: mark the pull request ready, comment on the issue, and keep answering reviews until the merge.\n- Never merge, tag, release, change the version, or push to another branch.\n\n## Plugins and roles\n\nA plugin is generic: a crate that implements core's `Plugin` trait. What it does comes from the roles it registers, each a trait in core: tracker, forge, agent, checks, stage. `plugins/github` registers two roles, tracker and forge (see [Assembling the binary](#assembling-the-binary)). A project has one forge and one agent, and any number of trackers, such as `github` and `jira` together. atelier finds a project's plugins, and a project names one only when it differs ([Configuration](#configuration)).\n\n| Role | Trait | Does | First plugin |\n| --- | --- | --- | --- |\n| Tracker | `Tracker` | Finds issues marked for building that match the filter; reads, marks, comments on and closes them; adds its part of the brief | `github` (#6), through `gh` |\n| Forge | `Forge` | Finds the pull request on a branch, its state and failed rounds; adds its part of the brief and its denied commands; defines how gates run in its CI | `github` (#6), through `gh` |\n| Agent | `Agent` | Starts a session in a worktree with the brief and permissions; interrupts it | `opencode` (#7), through `opencode api` |\n| Checks | `Checks` | Finds its roots in a tree; names each root's gates, proofs and fixes as commands. A language plugin is found; others are chosen | `rust` (#2), `tla` (#3), `typescript` (#4) |\n| Stage | `Stage` | Runs once every check passes, before the pull request is ready; reports passed, or failed with findings | `critic` (slice 7), `recording` (slice 8) |\n\nThe `Tracker` and `Forge` traits follow the data model of [forges](https://github.com/danielroe/forges): issues, pull requests, checks and labels, each plugin declaring the operations it supports. A project whose plugin lacks one atelier needs, such as marking an issue, fails `atelier init` with its name. A Jira tracker, or a GitLab or Forgejo forge, then fits without changing core.\n\nNot plugins, each with one implementation and no second in sight:\n\n- **Git** (`crates/git`): worktrees and branches, behind core's `Worktrees` trait so tests stand it in. Every forge and agent here works on a Git checkout.\n- **State and the lock**: in the CLI.\n- **R2**, where the recording stage keeps videos: one store.\n\n### Assembling the binary\n\nEach plugin's `register` adds the roles it fills, under the plugin's name:\n\n```rust\n// plugins/github/src/lib.rs\nimpl Plugin for GitHub {\n    fn name(&self) -> &'static str {\n        \"github\"\n    }\n\n    fn register<'a>(&'a self, registry: &mut Registry<'a>) {\n        registry.tracker(self);\n        registry.forge(self);\n    }\n}\n```\n\nThe CLI only lists the crates it was built with:\n\n```rust\n// crates/cli/src/plugins.rs\nlet plugins: [&dyn Plugin; 4] = [&GitHub, &OpenCode, &Rust, &Tla];\n```\n\nA project names its plugins by name: one forge, one agent, any number of trackers. Roots are found in the pull request's own tree, so a new crate or spec is checked in the pull request that adds it. A gate whose tool a project has not set up fails and says what to add.\n\n### The checks role\n\nA checks plugin reads the tree through core's `Tree` trait and returns data: its roots, and each root's gates and fixes as commands with their setup. It does no I/O itself, so it is tested with an in-memory tree:\n\n```rust\nlet roots = rust.roots(&tree);\n// → [Root { path: \".\", kind: \"workspace\" }]\n\nlet gates = rust.gates(&tree, &roots[0], \"origin/v2\");\n// → [Gate { name: \"fmt\", setup: [..], run: \"cargo fmt --all -- --check\" }, …]\n```\n\n`atelier check --setup` runs each gate's setup first, such as a toolchain or a frozen install.\n\n### Fixes before each commit\n\nWhat a tool can fix never reaches CI. A checks plugin names its fix commands beside its gates, such as `cargo fmt` and `cargo clippy --fix` for Rust or `oxfmt` and `oxlint --fix` for TypeScript, and `atelier fix` runs them on the roots a set of files touches.\n\nWhen atelier makes a builder's worktree, it gives that worktree alone a pre-commit hook, through Git's per-worktree config:\n\n```sh\ngit -C <worktree> config extensions.worktreeConfig true\ngit -C <worktree> config --worktree core.hooksPath ~/.local/share/atelier/hooks\n```\n\nThe hook runs `atelier fix --staged`, re-stages the files it changed, and then runs the project's own pre-commit hook, if it has one. Every commit the builder makes is already formatted and lint-fixed, and the builder does nothing for it. A staged file that also has unstaged changes is left alone, so no unstaged work slips into the commit; CI's format and lint gates catch what remains. The project's checkout and other worktrees keep their own hooks.\n\nVerified in a temporary repository: an unformatted staged file is committed formatted; a file with unstaged changes is committed as staged; a project hook still runs; the main checkout has no atelier hook.\n\n### Overrides\n\nA project overrides what is found only where it needs to, by path, in [`.atelier/config.toml`](#configuration):\n\n```toml\n[paths.\"vendor\"]\nchecks = []                     # nothing under vendor/ is checked\n\n[paths.\"tools/codegen\"]\n# generated code: mutants would only test the generator\nskip = [\"rust/mutants\"]\n```\n\n`checks` sets which checks plugins run in that subtree; `skip` drops named gates there. The deepest matching path wins. `atelier gates` shows the result, so an override can be checked before it is pushed.\n\n### The forge's CI\n\n`atelier init` asks the forge to write the project's CI. The `github` forge writes a workflow that calls its reusable `gates.yml`, pinned by commit:\n\n```yaml\n# .github/workflows/atelier.yml\njobs:\n  gates:\n    uses: StevenJPx2/atelier/.github/workflows/gates.yml@<sha>\n```\n\n`gates.yml` installs atelier from its release, reads `atelier gates --json --diff` into a matrix, and runs `atelier check --setup --gate <gate> --root <root>` as one job per gate and root, so each shows as its own check, such as `rust/clippy (.)`.\n\nVerified with a stand-in checks plugin in the tests, whose gates pass or fail on demand: roots in several directories, a `[paths]` override, a diff that touches one root of two, and a failing gate; and `gates.yml` on a fixture repository, where each gate shows as its own check.\n\n## Dependencies\n\nApproved.
